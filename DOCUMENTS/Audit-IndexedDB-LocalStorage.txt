Update pattern
Every write:

readProjects() — parse entire array
Find project by layout.id
Replace one array field (or push grid)
saveProjects() — stringify and overwrite entire array
Whole-array replacement for vines, treatments, objects, texts, rows — not incremental patches.

Race conditions / inconsistency risks
Last-write-wins across tabs — no versioning, locking, or merge.
Dual React + storage state — vines, treatments, etc. live in React while grids live only in projectData. A bug in one persist* path could desync slices.
ensureLayoutRows not auto-persisted — missing rows exist in React but not in storage until a row edit or new grid.
layout.lastEditedAt never updated on edits despite field existing.
addGridToLayout + updateLayoutRows — two separate writes when creating a grid (non-atomic; crash between them leaves partial state).
No validation on read — corrupt JSON throws; no schema versioning.
Treatment import reads other projects via getAllProjects() — cross-project read of full blobs.
Orchard embedded per project — same orchard concept cannot be shared; duplication if multi-project same orchard is needed later.
Accidental duplication
Orchard data duplicated: embedded object + layout.orchardId reference.
Entity arrays duplicated in React state and inside projectData after each persist (partial mirror).
useLayoutEditor duplicates types/state already in types/index.ts and TestGridClient.
4. Problems / Risks
Before IndexedDB
TestGridClient god component — persistence, domain logic, and UI intertwined; expensive to test and migrate.
Split state model — grids in projectData, everything else in separate useState; high refactor cost.
Document blob storage — loading one layout loads entire project + all entities; won't scale.
No migrations/version field — schema changes are manual and fragile.
Before sync / backend
No updatedAt on entities — only Project.createdAt and Layout.lastEditedAt (stale).
No soft deletes — hard deletes only; sync tombstones impossible without retrofits.
No revision / etag per entity — conflict resolution will be guesswork.
ID scheme not guaranteed globally unique under multi-device concurrent creation.
Flat vine array — no layout FK on Vine; integrity enforced only by app logic.
Row orphan risk — if grid row count ever changes, no cleanup of Row records (not implemented today).
Treatment delete — blocked if vines reference it (good), but no cascade/orphan policy documented.
1:1 Project–Layout assumption baked into storage shape — multi-layout projects would require structural change.
Orchard as reusable catalog (types comment §15) vs embedded copy (implementation) — mismatch will hurt multi-project orchards.
Expensive to change later
Monolithic ProjectData blob → normalized stores
Split React state → single source of truth / query layer
Array-level writes → entity-level CRUD with transactions
Adding sync metadata retroactively to all entities
Home page / project list (currently fake data)

Relationships
Keep FK fields on each record (layoutId, gridId, etc.).
Do not nest children inside parent records.

  → put grid
  → putAll rows
Query patterns
